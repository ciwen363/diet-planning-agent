# Diet Agent 前端改造执行计划

> 状态：已执行  
> 目标仓库：`diet-planning-agent`  
> 适用范围：现有原生 HTML / CSS / JavaScript 单页应用  
> 核心原则：先保证功能与错误反馈可信，再改善视觉；不改后端接口和业务语义，不做框架迁移。

## 1. 当前问题与已完成排障

### 1.1 截图中的 500 错误

截图中连续出现“这轮请求失败了，请稍后重试”和 `Internal Server Error`。已确认根因不是前端样式或意图识别，而是本地 `diet_db` 数据库虽然存在，却没有业务表，创建会话时访问 `diet_sessions` 即失败。

本地已导入仓库自带的 `src/main/resources/db/diet_db.sql`，当前有以下 6 张业务表：

- `diet_sessions`
- `diet_messages`
- `diet_request_trace`
- `diet_slot_option`
- `meal_item`
- `recommend_feedback`

独立端口验证结果：

- 会话创建成功；
- 使用问题“今天心情一般，想吃点热乎的”调用聊天接口成功；
- 系统返回澄清问题“今天想什么时候吃呢？是午餐还是晚餐？”；
- Trace 状态为 `SUCCESS`，共采集 11 个事件。

执行前请先在 IDEA 中停止旧的 8080 进程并重新运行一次，再从浏览器创建新会话验证。前端改造不得通过吞掉错误或伪造成功响应来“修复”该问题。

### 1.2 首次提交前的仓库安全前置项

当前 `application.yml` 中存在明文服务凭据。首次提交或推送前必须：

1. 立即轮换已经写入文件的服务密钥；
2. 把服务密钥与数据库密码改为环境变量读取；
3. 提供不含真实凭据的 `application.example.yml` 或 README 配置示例；
4. 检查 `.gitignore`，完整忽略 `.idea/`、本地运行配置和其他机器私有文件；
5. 使用 `git diff --cached` 再次确认暂存区没有真实密钥。

这属于仓库发布前置工作，不属于本次前端视觉改造，执行 Agent 不得跳过，也不得擅自提交当前凭据。

## 2. 改造目标

本轮前端改造解决四件事：

1. **层级清楚**：用户一眼看懂“开始推荐—补充条件—查看结果—反馈”的主路径；
2. **聊天好用**：输入区始终可达，请求中、失败、重试和继续对话都有明确反馈；
3. **视觉克制**：从大面积浅绿色、超大圆角和重阴影，调整为温暖中性色加少量品牌绿；
4. **研发能力不抢主流程**：Trace 和评估仍保留，但在导航中明确归为研发工具。

不以“更炫”为目标，不引入与饮食推荐无关的装饰动画，也不虚构后端暂未提供的会话历史、登录、头像或实时流式输出能力。

## 3. 范围与硬性约束

### 3.1 本轮包含

- 首页、聊天推荐、个人餐食、公共餐食、Trace、评估六个现有路由的视觉统一；
- 聊天页信息架构、消息状态和错误重试体验；
- 桌面、平板、手机响应式布局；
- 键盘操作、焦点样式、对比度和动态状态提示；
- 对 `app.js` 做必要的渲染函数拆分，降低继续维护的难度；
- 对 `api.js` 增加标准错误对象、请求超时与可取消能力。

### 3.2 本轮不包含

- 不修改后端 Controller、DTO、接口地址、请求字段或响应字段；
- 不调整意图识别、槽位规则、Agent 编排、推荐算法或评分逻辑；
- 不迁移到 React、Vue 或其他框架，不新增构建链；
- 不新增后端没有支持的会话列表、账号体系、图片上传或流式对话；
- 不删除 Trace、标注和评估能力。

## 4. 信息架构

### 4.1 顶部导航

当前导航项目过多，用户功能和研发功能混在一层，用户 ID 也过于抢眼。改为：

- 左侧：品牌标识“Diet Agent / 饮食推荐助手”；
- 中部主导航：首页、聊天推荐、我的餐食、公共餐食；
- 右侧：`研发工具` 下拉入口，包含 Trace 与评估；
- 用户 ID 移入右侧紧凑的“体验设置”弹层，保留原有 `localStorage` 行为；
- 移动端使用菜单按钮展开导航，菜单必须支持键盘和 Escape 关闭。

不改变六个现有 hash 路由：

- `#/diet`
- `#/diet/chat`
- `#/diet/meals/personal`
- `#/diet/meals/public`
- `#/admin/traces`
- `#/admin/evaluations`

### 4.2 页面层级

- 用户页面强调任务和结果；
- 研发页面强调筛选、表格和详情；
- Session ID、Trace ID 等技术信息不再占据聊天主视觉，收进“本轮详情”折叠区；
- 快捷问题只在空会话或输入为空时重点展示，发生真实对话后弱化。

## 5. 视觉规范

### 5.1 色彩

- 页面背景：偏暖的浅灰白，而非整页薄荷绿；
- 品牌主色：保留绿色，但仅用于主按钮、当前状态、链接和关键反馈；
- 文本：深灰黑作为正文，次级信息使用中性灰；
- 成功、警告、失败分别使用语义色，失败不能继续沿用品牌绿色；
- 所有正文与背景达到 WCAG AA 对比度。

### 5.2 字体、间距与形状

- 延续系统中文字体栈，不加载外部字体；
- 使用 8px 间距体系：8 / 12 / 16 / 24 / 32 / 48；
- 页面主标题 28–32px，卡片标题 18–20px，正文 14–16px；
- 卡片圆角控制在 12–16px，按钮 10–12px；
- 阴影只用于浮层和关键卡片，普通容器以边框和背景层级区分；
- 控件最小点击区域 44×44px，焦点环清晰可见。

### 5.3 布局断点

- ≥ 1200px：内容最大宽度约 1440px，聊天主区 + 280px 辅助栏；
- 768–1199px：辅助栏折叠为可展开区域；
- < 768px：单列布局，导航折叠，输入框和主按钮仍在同一可达区域；
- 重点验收宽度：1440、1024、768、390px，均不得出现横向滚动。

## 6. 聊天页详细方案（最高优先级）

### 6.1 页面结构

1. 顶部任务栏：页面标题、数据源分段控件、创建新会话；
2. 消息区：内容列最大宽度 760–820px，避免消息横跨整屏；
3. 辅助区：快捷问题、使用说明、本轮详情；
4. 底部输入区：在聊天容器底部保持可见，包含多行输入、发送按钮和简短状态提示。

`个人库 / 公共库` 使用真正的单选分段控件，当前选择必须同时由文字、颜色和 `aria-checked` 表达；“新会话”是独立次级按钮，不能和数据源看起来像同组单选项。

### 6.2 消息呈现

- 用户消息右侧，助手消息左侧，宽度随内容变化但不超过消息列；
- 不必添加虚构头像，用“你 / 饮食助手”的轻量角色标签即可；
- 澄清问题与最终推荐在视觉上有区别；
- `missingSlots` 显示为对用户可理解的“还需要：用餐时间、健康目标”，不要直接暴露后端字段名；
- Trace ID 放入本轮详情，提供跳转 Trace 页的入口；
- 相邻重复错误不得生成多条相同助手消息。

### 6.3 请求中状态

提交后立即：

1. 保留并展示用户消息；
2. 清空输入框，但在失败时允许一键恢复原问题；
3. 添加单个助手“正在理解你的需求…”占位消息；
4. 暂时禁用重复提交，发送按钮显示进行中状态；
5. 响应回来后原位替换占位消息，不整页重绘，不抢走输入框焦点。

### 6.4 错误与重试

建立统一的 `ApiError`，至少保存：HTTP 状态、后端消息、是否超时、原始请求上下文。聊天接口失败时：

- 在对应消息位置显示一条内联错误卡，而不是同时追加错误消息和弹出原始英文 toast；
- 文案按类型区分：网络不可达、请求超时、服务端异常、业务校验失败；
- 错误卡提供“重试本轮”按钮，复用原 session、sourceMode 和 message；
- 同一个请求只能存在一个错误卡，多次点击时按钮进入 loading，禁止并发重试；
- `Internal Server Error` 等后端原始文本只放到可展开的开发详情里；
- toast 保留给餐食保存、删除、反馈等短操作，不用于重复呈现聊天错误。

`api.js` 增加超时和 `AbortController`，超时时间统一配置；路由切换或新会话时取消仍在进行的聊天请求，避免旧响应写入新会话。

### 6.5 推荐卡与反馈

推荐餐食卡按以下顺序展示：

1. 餐食名称与一句推荐理由；
2. 与本轮需求匹配的标签；
3. 分数或来源信息（仅展示响应中真实存在的数据）；
4. 有用 / 不合适反馈操作。

反馈提交中按钮禁用，成功后保留已选状态；失败时原位提示并允许重试，不弹出遮挡内容的全局错误。

## 7. 其他页面方案

### 7.1 首页

- 首屏只保留一句价值主张、主操作“开始推荐”和次操作“维护我的餐食”；
- 用三步说明“说需求—补条件—给推荐”；
- 统计数据请求失败时显示轻量占位，不影响开始聊天；
- Trace 入口放在研发工具区域，不与用户主入口并列。

### 7.2 个人餐食

- 桌面端采用列表 + 编辑面板，移动端改为列表后进入表单；
- 新增和编辑状态有清晰标题，未保存离开时提示；
- 标签多选按槽位分组，选中态、禁用态和空状态明确；
- 删除需要二次确认，成功后只刷新对应列表区域。

### 7.3 公共餐食

- 加入轻量筛选与结果数量；如果接口暂不支持服务端筛选，仅做当前结果的前端筛选；
- 卡片结构与推荐卡复用，但不显示个人编辑操作；
- 空状态引导返回聊天页，不伪造公共餐食数据。

### 7.4 Trace

- 搜索条件放在可折叠筛选栏；
- 桌面端左表右详情，窄屏改为列表进入详情；
- 状态、耗时和错误类型使用统一标签；
- JSON / 事件详情使用等宽字体和可滚动区域，默认折叠大段原始数据；
- 标注保存状态明确，避免整页重绘后丢失当前选中 Trace。

### 7.5 评估

- 先展示运行参数和“开始评估”，运行中显示真实进度能力；若后端没有进度接口，只显示不可伪造百分比的等待态；
- 报告先展示核心指标，再展示样本明细；
- 指标提供中文解释，空报告显示下一步操作；
- 失败时保留刚才填写的参数并允许重试。

## 8. 文件级实施建议

### 第一阶段：低风险视觉基线

- `index.html`：调整 header 语义结构、研发工具菜单、体验设置入口和跳过导航链接；
- `assets/css/app.css`：重建 tokens、布局、按钮、表单、卡片、状态和响应式规则；
- 保留现有脚本加载方式，先不拆模块，确保视觉改动可以独立验收。

### 第二阶段：聊天状态修正

- `assets/js/api.js`：加入 `ApiError`、超时、取消信号和一致的错误解析；
- `assets/js/app.js`：为每次聊天请求记录唯一 request id、pending/error 状态和原请求参数；
- 将 `renderChat()` 拆为页面壳、消息列表、消息项、推荐卡、辅助栏和输入区等小函数；
- 更新单条消息或局部区域，避免每次发送都重建整个聊天 DOM。

### 第三阶段：其余页面组件统一

- 抽取并复用按钮、状态标签、空状态、加载骨架、错误卡、确认弹层、分页/筛选栏；
- 统一餐食卡在聊天、个人库和公共库中的结构；
- 统一 Trace 与评估页面的表格、详情和表单样式。

如第二阶段后 `app.js` 继续显著膨胀，再在不引入构建工具的前提下改为原生 ES Modules，例如：

- `assets/js/core/api.js`
- `assets/js/core/state.js`
- `assets/js/core/router.js`
- `assets/js/components/`
- `assets/js/views/`

模块拆分是维护性步骤，不得阻塞第一轮视觉和聊天错误态交付。

## 10. 验收清单

### 功能回归

- 六个既有路由均可直接访问和刷新；
- 用户 ID 修改后仍通过 `X-User-Id` 传递并持久化；
- PERSONAL / PUBLIC 模式切换准确，新会话可创建；
- 聊天澄清、推荐、反馈链路可用；
- 个人餐食增删改查、公共餐食读取正常；
- Trace 搜索、查看和标注正常；
- 评估提交与报告展示正常。

### 聊天专项

- 发送过程中只有一个 pending 状态，不能重复提交；
- 成功响应原位替换 pending，不产生重复消息；
- 500、网络断开和超时分别显示可理解的错误；
- 点击重试只重放失败的一轮，保留原 session、模式和问题；
- 切换路由或新会话后，旧请求不会污染新页面；
- 输入框在正常交互后仍保持合理焦点。

### 视觉与可访问性

- 1440 / 1024 / 768 / 390px 无横向滚动和关键控件遮挡；
- 键盘可以访问导航、菜单、表单、分段控件、反馈和重试；
- 可见焦点、表单标签、错误关联、`aria-live` 状态完整；
- 正文和操作控件达到 WCAG AA 对比度；
- 不依赖外部 CDN、图片或字体才能正常使用。
